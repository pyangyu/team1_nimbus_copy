# Thinking Brownout: where the code stands (2026-10-22)

## The idea in one paragraph

When a burst overloads an LLM service, a rate limiter turns users away, a queue lets
latency grow, and scale-out arrives minutes after the burst. Thinking Brownout serves
everyone a little cheaper instead. As vLLM's queue backs up, it shrinks the thinking
budget of requests that are already decoding, in proportion to the pressure. It can tell
the model about the cut (`<budget_cut left=N>`), and the plan is to train the model to
finish well with less. A small decision model, Open-Jev, predicts how long each request
will think so that cuts land on the requests that can afford them.

### Pressure and cuts
- `p = min(1, waiting / running)` from vLLM `/metrics`, every 0.5 s. Nothing is cut below
  `p = 0.05`.
- Every 0.25 s, each running request's limit becomes `max(budget × (1 − min(0.9, p·w)), used + 64)`.
  The budget is the predicted bucket's upper edge, capped at what the client asked for. `w` is
  the priority weight: high 0.5, normal 1, low 1.5.
- `silent`: the request stops at the new limit. `announced`: the gateway continues the request
  with `<budget_cut left=N>` appended, so the model can wrap up on its own terms. A later drop
  of at least `max(64, 0.1 N)` tokens sends a new notice with the new N.

### Prediction
- **Open-Jev-2B** (Qwen3.5-2B + LoRA + scoring head, one A10G) answers one 10-level score
  question per request: which thinking bucket (0–32 tokens up to 16K+). It answers the
  priority in the same call. Its prompt includes the most similar recently finished requests
  and the thinking they used, so it calibrates to the live model in context. Its weights do
  not change yet.
- **Jev runs beside the LLM, not before it.** Jev is prefill-only, so a call (~0.08 s warm)
  takes about as long as the LLM's prefill. The gateway sends the request to vLLM and queues
  it for Jev at the same moment. The answer typically lands as decoding starts, which is
  where cuts happen. When Jev is busy, requests queue; the one with the fewest decoded tokens
  goes next, so requests still waiting in vLLM's queue get their budget before they decode.
- **Word model** (hashed words and bigrams → softmax, one AdaGrad step per finished request).
  It no longer sets budgets; it predicts every request beside Jev as the comparison point.
- **Labels** are free: a request that closes `</think>` itself gives its exact bucket; a cut
  one gives "at least this bucket".

### Baselines and predictor variants (gateway `--policy`, `--predictor`)

| Name | What it does |
|---|---|
| `none` | Nothing; the queue grows |
| `reject` | Token bucket on new workflows (classic rate limiter) |
| `uniform` | Cut every request by the same fraction; no prediction |
| `brownout:…:jev` | Untrained Jev beside the LLM sets budgets and priorities |
| `brownout:…:jev-serial` | The gateway waits for Jev before sending to vLLM |
| `brownout:…:online` | The word model sets budgets |
| `brownout:…:oracle` | The thinking length the same prompt used in an earlier uncut run (upper bound) |
| `brownout:…:jev-learn` | Trained Jev (skipped until the learner exists) |

## The experiment

The CI job `brownout-e2e` runs on every push to `main`. It brings up the three AWS boxes and
runs each variant as a burst of agent workflows. Before each run, the classifier state is reset,
so no variant gets a head start from the runs before it.

- **GSM8K sweep:** 64 workflows arriving at 4/s, thinking budget 1024 (retries up to 2048).
- **MATH-500 sweep:** 32 workflows at 2/s, budget 4096 (retries up to 6144). Harder problems
  spread across more buckets, so prediction has more to do.

Metrics per run:
- **Outcome:** accuracy, deadline met, correct and on time, latency.
- **Cuts:** how many requests were cut or announced.
- **Jev timing:** when Jev's answer landed (before the first token or during decode), time
  in the Jev queue, and the added wait in serial mode.
- **Prediction quality:** exact, within-one-bucket and under-prediction rates for Jev and the
  word model, on the same requests.

### Jev timing (all runs together)
- **Jev answered 1,345 of 1,346 calls** with no failures.
- **When the answers landed:** 466 before the first token, 879 during decode, 1 after the request
  finished.
- **Answers changed the budget:** Jev lowered the bucket 400 times and raised it 280 times. It
  changed the priority 835 times.
- **Queue wait:** a mean of 2.0 s with one Jev worker. Bursts queue up, which is why most
  answers land during decode.
- **Serial mode cost:** gating vLLM on Jev added 3.5 s per request on GSM8K and 1.0 s on MATH-500.

### Bucket accuracy, Jev against the word model on the same requests
In the GSM8K `none` run (73 paired requests, nothing cut):

| | Exact | Within one bucket | Under-predicted |
|---|---|---|---|
| Untrained Jev | 0.18 | 0.73 | 0.21 |
| Word model | 0.53 | 0.81 | 0.01 |

In the MATH-500 `none` run (17 requests), both under-predict most of the time: Jev 0.88, the
word model 0.82. Neither has seen many long-thinking requests.

### What this says
1. **Brownout beats the classic baselines.** On GSM8K, announced brownout reaches 0.95 correct
   and on time. `none` reaches 0.67, because the queue blows deadlines. `reject` reaches 0.17,
   because it turns most users away.
2. **Brownout matches `uniform` but doesn't clearly beat it.** The gap is 0.95 against 0.92 on
   GSM8K, with 10% less thinking. On MATH-500, `uniform` ties or wins. With 32–64 workflows a
   run, 3 points is one or two workflows. The predictor isn't buying much yet.
3. **Parallel Jev beats serial Jev on GSM8K.** It scores 0.95 against 0.92 and its p50 is 8 s
   better, because serial mode waits for Jev before vLLM starts. The answers still arrive in
   time: two thirds land during decode, where cuts happen.
4. **Untrained Jev guesses buckets worse than the word model.** It is exact 18% of the time
   against 53%, and it under-predicts more often. Outcomes tie anyway, since the controller's
   floor (`used + 64`) and announced cuts absorb the errors. This is the case for the Jev
   learner: in-context examples alone don't calibrate it.
5. **Hard problems cost accuracy.** On MATH-500, every cut policy loses 13–16 accuracy points
   against `none` (0.72), in exchange for meeting every deadline. That accuracy is what the
   cut-trained model (SFT/RL) is meant to win back.
6. **The oracle helps less than expected.** On MATH-500 it found an earlier uncut length for
   only 21% of requests and fell back to the requested budget otherwise. A real upper bound
   needs a full uncut pass over the same prompts first.
